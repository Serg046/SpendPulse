# SpendPulse

## C# conventions

- Do not suffix method names with `Async`, even for async methods (e.g. `Get()`, not `GetAsync()`). This applies to methods we write; third-party library APIs (e.g. `MongoDB.Driver`) keep their own naming.
- Do not default to `*OrDefault` methods (`FirstOrDefault`, `SingleOrDefault`, etc.) out of habit. Prefer throwing variants (`First`, `Single`) unless a missing result is a genuinely expected, legitimate case for that query.

## Blazor conventions

- No SignalR. Never use `@rendermode InteractiveServer` or `InteractiveAuto`, and never call `AddInteractiveServerComponents()`/`.AddInteractiveServerRenderMode()` in `Program.cs`. Always use `@rendermode InteractiveWebAssembly`. Interactive Server (and Auto's first-load fallback to it) requires a persistent SignalR circuit to `/_blazor`, which breaks across multiple replicas without session affinity/sticky sessions configured at the ingress — this bit us in production (WebSocket/LongPolling connection failures on first load after deploy). WebAssembly has no such requirement: it still gets server-side prerendering for a fast first paint, then runs entirely client-side over plain HTTP calls to the API, same as this app's existing `*ApiClient` classes already do.
- Money amounts in the UI must always show exactly 2 digits after the decimal point (e.g. `29.98`, `50.00`, not `50`). Raw stored amount strings aren't guaranteed to have 2 decimals, so parse as `decimal` and format with `.ToString("0.00", CultureInfo.InvariantCulture)` rather than displaying the raw string.
- For any `@rendermode InteractiveWebAssembly` page/component that fetches data in `OnInitializedAsync`, persist the fetched data via `[PersistentState]` properties and guard the fetch (e.g. `if (SomeProp is not null) { return; }`). Otherwise the component's `OnInitializedAsync` reruns and refetches everything a second time when the page hands off from the server prerender to WebAssembly, causing a visible content "reload" flash. See `Transactions.razor`'s `TransactionList` and `Merchants.razor`'s `MerchantNames`/`Mappings` for the established pattern.
- Child components should not independently re-fetch reference data (e.g. merchant mappings/group assignments) that an ancestor `@rendermode InteractiveWebAssembly` page already loads and persists via `[PersistentState]`. Pass the already-loaded data down as a `[Parameter]` instead. Otherwise the child's own `OnInitializedAsync` fetch reruns on the prerender→WebAssembly handoff exactly like the unguarded-fetch case above, even though the parent did it right. See `CreditorSummary.razor`/`GroupSummary.razor` receiving `Mappings`/`GroupAssignments` from `Transactions.razor` for the established pattern.
- In SVG markup, never interpolate a raw `double` into a numeric attribute (`x`, `y`, `cx`, `cy`, viewBox, etc.) — Blazor's default `ToString()` uses the current culture, which may format decimals with a comma (e.g. `226,72486`), producing invalid SVG that the browser silently drops. Always format explicitly with `.ToString(CultureInfo.InvariantCulture)`.
- Never write an SVG `<text>` element directly in `.razor` markup. Razor's parser treats a bare `<text>` tag as its own "literal markup transition" syntax (used to emit plain text without a wrapping element), not as the SVG element — it silently emits no `<text>` DOM node at all, so any nested `<tspan>` renders nothing (a `<tspan>` outside a `<text>` parent is invalid SVG). Build SVG text as a raw HTML string (HTML-encode any interpolated content) and render it via `MarkupString` instead. See `Trends.razor`'s `RenderYAxisLabels`/`RenderXAxisLabels` for the established pattern.
- No `.js` files in `wwwroot`. Things that look like they need JS interop (click-outside-to-dismiss, closing a menu, clearing a selection) almost always have a pure-Blazor equivalent — e.g. `@onclick` on a wrapping element plus `@onclick:stopPropagation="true"` on the parts that shouldn't trigger it, relying on Blazor's own event bubbling. See `Transactions.razor`'s `ClearSelection`/row menu for the established pattern. Only reach for `IJSRuntime` when the browser API has no C# equivalent at all (clipboard access, element geometry via `getBoundingClientRect`, scroll position). Even then, don't add a `.js` file — inline the script as a C# string constant and import it as a `data:text/javascript,...` URI (see `Groups.razor`'s `DragScrollModuleSource`), so there's still nothing to keep track of on disk.
- Never call `DateTime.ToLocalTime()`, `DateTime.Now`, or `DateTime.Today` for display or date-range logic in a `@rendermode InteractiveWebAssembly` page/component. That code runs twice — once server-side during prerender (the container's local time, effectively UTC) and once client-side during hydration (the browser's local time) — so `ToLocalTime()`/`Today` produce different results on each pass, causing a visible mismatch/flash (and for persisted `[PersistentState]` date values, can even flip the value by a day near midnight). Use `AppTimeZone.ToDisplayTime(utc)` / `AppTimeZone.Today` (`SpendPulse.Client/Services/AppTimeZone.cs`) instead — it converts to a fixed `Europe/Sofia` time regardless of where the code executes, so server and client always agree. MongoDB storage stays UTC (`DateTime.UtcNow`) as always; only the display layer uses `AppTimeZone`. See `SyncStatus.razor`, `Transactions.razor`, and `Trends.razor` for the established usage.
